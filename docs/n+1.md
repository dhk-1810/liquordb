## N+1 및 쿼리 최적화 가이드

### 0. 전역 지연 로딩 기본 전략

- 모든 `@ManyToOne`, `@OneToOne` 연관관계에 기본 `FetchType.LAZY`를 명시하여 불필요한 즉시 로딩(EAGER)으로 인한 쿼리 폭포수 원천 차단.


### 1. QueryDSL 페치 조인 (`fetchJoin`)

- **원리**: 연관된 엔티티를 별도 쿼리로 분리하지 않고 한 번의 SQL `JOIN`으로 즉시 함께 가져오는 방식.
- **적용 사례**:
  - `CommentRepositoryImpl.findByReviewId()`: 댓글 목록 조회 시 연관된 `user`, `review`, `review.liquor`를 3단 페치 조인(`leftJoin(...).fetchJoin()`)하여 단일 쿼리로 조회.
  - `ReviewRepositoryImpl.findByLiquorIdWithTags()`: 리뷰 목록 조회 시 `user`, `reviewTags`, `tag`를 페치 조인.


### 2. MultipleBagFetchException 방지 전략 (페치 조인 + 배치 패치 하이브리드)

- **문제 배경**:
  - Hibernate는 2개 이상의 `List` 컬렉션(Bag)을 동시에 페치 조인할 경우 카테시안 곱으로 인한 메모리 데이터 왜곡을 방지하기 위해 `MultipleBagFetchException: cannot simultaneously fetch multiple bags` 예외를 발생시킴.
- **프로젝트 내 조치 현황**:
  - `Review` 엔티티는 `reviewTags`(`List<ReviewTag>`)와 `imageKeys`(`List<ReviewImageKey>`)라는 2개의 컬렉션을 보유하고 있음.
  - **하이브리드 분리 전략**:
    1. `ReviewRepositoryImpl`: 컬렉션 중 **`reviewTags` 1개만 `fetchJoin()`**을 적용.
    2. `imageKeys`: 페치 조인하지 않고 지연 로딩(LAZY)으로 유지.
    3. `ReviewService`: `review.getImageKeys()` 호출 시 `default_batch_fetch_size: 100`이 동작하여 `IN` 쿼리로 묶어서 한번에 가져옴.
       -  **`WHERE id IN (?, ?, ...)`**
  - 2개 이상의 Bag을 동시 페치 조인하지 않으므로 **`MultipleBagFetchException`이 발생하지 않음.


### 3. 대량 데이터 수정/삭제 시 벌크 연산 (`@Modifying`)

- **원리**: 자식 엔티티들을 건건이 `SELECT`하여 Dirty Checking(변경 감지)으로 개별 `UPDATE`/`DELETE`를 수행하면 $N$번의 쿼리가 발생하므로, JPQL 직접 벌크 쿼리로 1번에 일괄 처리.
- **영속성 컨텍스트 동기화**: 벌크 연산은 1차 캐시를 우회하고 DB에 직접 반영되므로, 데이터 불일치를 방지하기 위해 반드시 **`@Modifying(clearAutomatically = true)`**를 적용하여 연산 직후 영속성 컨텍스트를 초기화.
- **적용 사례**:
  - `CommentRepository`: 리뷰나 주류 삭제 시 연관된 댓글들을 일괄 소프트 삭제/복구하는 쿼리 (`softDeleteCommentsByReview`, `softDeleteCommentsByLiquor`, `restoreCommentsBy...`)
  - `ReviewRepository`: 주류 삭제 시 연관 리뷰 일괄 소프트 삭제 (`softDeleteReviewsByLiquor`)


### 4. 애플리케이션 레벨 배치 IN 조회

- **원리**: 목록 응답 시 각 항목마다 "현재 유저가 좋아요를 눌렀는지(`likedByMe`)" 여부를 루프 돌며 `existsBy...`로 조회하면 목록 크기($N$)만큼 쿼리가 추가 실행됨.
- **해결 방식**:
  1. 조회된 엔티티 목록에서 ID 목록(`List<Long> ids`)을 추출.
  2. Repository에 `IN (:ids)` 쿼리 1번을 날려 내가 좋아요 누른 ID `Set`을 일괄 획득.
  3. DTO 변환 시 메모리상에서 `likedIds.contains(id)`로 $O(1)$ 즉시 매핑.
- **적용 사례**:
  - `ReviewService.getCursorPageResponse()`: `reviewLikeRepository.findLikedReviewIdsByUserIdAndReviewIds(userId, reviewIds)`
  - `LiquorService.findAll()`: `liquorLikeCacheService.getLikedLiquorIds(userId, liquorIds)`


### 5. 서브쿼리 기반 단일 DTO 프로젝션 (Multi-Count 최적화)

- **원리**: 마이페이지 등에서 여러 엔티티의 활동 카운트(리뷰 수, 댓글 수, 좋아요 주류/리뷰/댓글 수 등 총 5개)를 각각 `count()`로 5번 날리지 않고, 단 1번의 쿼리로 서브쿼리 집계.
- **적용 사례**:
  - `UserRepositoryImpl.getUserActivityCounts()`:
    - QueryDSL 서브쿼리(`JPAExpressions.select(count())`) 5개를 결합하고 `Projections.constructor(UserActivityCountDto.class, ...)`를 사용하여 **단 1번의 SELECT 쿼리**로 모든 집계 결과를 일괄 반환.


### 6. Redis Cache-Aside를 통한 DB 조회 제거

- **원리**: 자주 조회되는 유저의 좋아요 상태 데이터를 Redis Set 자료구조에 캐싱하여 목록 조회 시 발생하는 DB 쿼리 자체를 차단.
- **적용 사례**:
  - `LiquorLikeCacheService.getAllLikedLiquorIds()`: 주류 목록 조회 시 Redis 캐시가 존재하면 DB 조회를 전혀 수행하지 않고 Redis Set에서 조회하여 응답 조립.
